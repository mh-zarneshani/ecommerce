# spec.md — Ecommerce accounts / bootcamp MVP

**Outcome:** In a 3-minute Persian RTL demo (local or access-controlled VPS), a manager sees the first issue worth investigating; a specialist can trace the evidence, change or reject the recommendation, approve an internal referral, and record the outcome. Build the app, not a design document. `acceptance.md` defines how to prove it works. This is a production-minded classroom prototype, not a production deployment.

## 1. Scope and sources
One process, one persisted local database, three workbook and manual-entry accounts (دیجی‌کالا `ACC-DIGI`, اکالا `ACC-OKALA`, اسنپ `ACC-SNAPP`), brand اکتیو, one category مایع دستشویی, three training product IDs, one month at a time. Reuse a suitable existing stack; for an empty repo use Python + Streamlit + PostgreSQL + openpyxl + pytest. `store.py` is an incomplete SQLite prototype, not the selected runtime. Follow §7 for the local build. Two views are enough: dashboard/ranked queue and case detail/timeline. Support explicit workbook import and stepping through the demo in the UI. Display the selected dataset, mode, reporting cutoff, grain, source and units. No external ecommerce connections, sending, changing price/order/budget, ads, sampling, product-matching project or causal sales claims.

Use separate dataset namespaces in every business key, join, tool and reset:
- **workbook:** `inputs/Active_Ecommerce_Bootcamp_Sample_Data(1).xlsx`, original read-only. Default بهمن, day 135 18:00. Only selected accounts/products. `دیکشنری داده` lists table ranges; header is row 4, notes are not data. Use `فروش روزانه` (business ID + revision; raw counts, discount, brand share), `برنامه ماهانه` (monthly target and **discount support**, not media), `کالاهای مرجع`, `جامعه عرضه`, `پایش عرضه`, `سیاست تخفیف`, `شواهد خواندنی`, `راهنما`. Raw offer titles and training product IDs are not verified barcodes. Use scoped training mappings; ambiguity requires review. Computed summary, reference, KPI and answer sheets are not runtime evidence. If using historical cases, reconstruct only events available by cutoff, not a case's final row. Do not implement unrelated workbook missions.
- **class-demo:** `inputs/class-demo.json` is synthetic. `initial` is a two-account checkpoint (Okala and Snapp only; no invented Digikala case); apply exactly one operator-selected branch afterward, not both. It deliberately differs from workbook totals and policies. Never load expected answers into app or planner.

## 2. Import and metrics (deterministic domain code)
Use one account registry for import, dashboard filters, plans and manual entry; report unknown account IDs rather than silently dropping them. Make acquisition replaceable: a reader maps its native records into typed sale, plan or offer-observation inputs for a common validation, provenance and persistence service. Preserve dataset, source, external ID, revision, account/product mapping, grain, units, event time, and availability time. UI, metrics and case rules depend on these normalized inputs, not workbook columns or store clients. Aggregate sales only under an explicit source/overlap rule; never add overlapping sources by default. In this phase the only inputs are local. For X1, inject a tiny in-memory test reader, not a live connector. In a later phase add individual, authorized read-only API or export readers to this same repo, with mapping, checkpoints/retry and contract tests; no assumption of provider access. Finance/sales and store-level price/stock are distinct capabilities. A connector must not send store commands or approve referrals.
Explicit import with counts and row-level reasons for invalid/conflicting rows. Normalize, validate then commit atomically. Same key + revision + canonical payload = no-op; higher valid revision replaces; lower is stale, not additive; same revision/different payload preserves conflict for review without silently choosing a new winner. Retain raw trace and last uncontested contribution; flag disputed aggregates. Plans without revision: identical rows no-op; changed content for same account/month/plan scope requires explicit review, never sum both. A file checksum may accelerate import; it is not the only deduplication mechanism.

Net packs = registered − cancelled − returned. Workbook spend (تومان) = net packs × reference unit price × consumer discount × brand share. Recompute from raw values; no cached financial formulas. Join aggregates at matching grain. Attainment = Σ actual / Σ target; utilization = Σ spend / Σ approved discount budget. No percent averages, cross-currency totals, target replication across SKU, or allocation of account targets to SKU. In this slice the account target covers the three training products together; don't invent a category or SKU target for a subset. An aggregate for a category is context, not SKU sales. Financial spend is not page discount. Missing values/zero denominators → «نامشخص» with reason; observed 0 sales with positive target → 0%. Retain precision until display.

Dashboard filters: account, month, brand. Show packs vs full-month target and signed gap (actual − target); show spend, budget and utilization. For workbook, label pace to cutoff separately: prorate monthly target using weight 1.4 on days 8–14 inclusive, 1 otherwise, normalized over the scenario month. No future sales as zeros; beyond data coverage show insufficient data. Workbook clock = (day−1)×24 + hour. Enforce observation time **and** evidence availability time ≤ cutoff. Latest accessible witness version only; age from observation time, not download time. Clock injectable, workbook max age 5 hours inclusive.

## 3. Rules, cases and control of writes
- Fresh confirmed unavailability may open a stockout **at the observed offer/store/location**. Track retrieval status, freshness, coverage and orderability separately. Failed fetch, stale data, no service coverage or uncertain mapping cannot prove unavailability or recovery. Such input on an existing case can change its next action, not close it.
- Page discount = (reference − sale)/reference. Compare unrounded value strictly `>` approved cap; first match approval, product, account, offer/location and observation-time validity; then apply policy priority including scoped exceptions. Unknown/zero reference, missing or conflicting applicable policy → needs review, not confirmed breach.
- At most one active episode per (dataset, issue type, account, product, offer, store, location). New evidence for same episode appends once. After closure a truly new incident starts a new episode. Replay is side-effect-free, including agent drafts and audit events. Late evidence may add history; older evidence cannot undo newer state.
- Keep **case** (open → recovery verified → owner closed) distinct from **proposal** (draft/edited → approved or rejected) and from **referral**. An approved proposal creates exactly one internal referral atomically, including on double-click. Store original and edited text, actor, owner, clock and evidence IDs. Reject ≠ refer. Same-scope fresh recovery after incident records result; only the owner explicitly closes. Simulated identities are acceptable only in local mode. On the VPS, enforce actor and owner permissions server-side using authenticated identities; never trust a UI role selector. Persist and display the timeline across process restart.

## 4. Agent contract
A newly accepted relevant observation triggers a bounded investigation and updates the open queue. The agent chooses the next read based on prior results; not a fixed chain with narrative added afterward. Expose narrow local tools for case/observation, evidence, valid policy and same-account category performance. Each result has IDs, scope and time. Treat witness content as data only. Only a validated internal draft may be written via the host; no agent tool to approve, refer, close, browse arbitrary URLs or execute instructions inside a witness. Use a per-round cap of 8 investigative calls and stop on lack of useful progress.

Use `prompts/triage-system.md` as the model-mode system prompt. Provide two implementations of the same interface: a repeatable offline evidence-driven planner (local/test default, no credentials) and a server-side online DeepSeek tool-calling adapter (intended VPS mode). Use an injected simulated transport for routine adapter tests. No local model required. Follow the hosting and privacy rules in §6. Validate both identically. Never silently substitute offline output for a model run: label mode, tool error and unverified live-model tests. Deterministic host owns arithmetic, policy, event IDs, permissions and lifecycle. Team preference for this demo: verified stockout in a category behind plan outranks verified excess discount; ties stable by case ID, never by account name. Uncertain new evidence goes to verification, not a confident stockout action. Store structured drafts, evidence timestamps, missing data, approval state and tool traces, not hidden chain-of-thought.

## 6. Access-controlled VPS and hosted model
- One Linux VPS, single app instance with persistent PostgreSQL separate from the release directory, TLS reverse proxy (e.g. Caddy with WebSocket support), domain set by operator. Document DNS A (AAAA only with working IPv6), ports, non-root app service, restart, online backup and restore check. Expose only proxy HTTP(S) and restricted admin SSH; no public Streamlit/DB port. Require login before access to app, including paid inference; map authenticated identities to authorized roles. No anonymous users may run/reset the demo or incur charges.
- `AGENT_MODE=deepseek`, `LLM_BASE_URL=https://api.deepseek.com`, `LLM_MODEL=deepseek-flash`, `DEEPSEEK_API_KEY` from server secret store/protected environment only. Never accept host/model/key from an end user; allowlist the HTTPS provider. Use the OpenAI-compatible chat completions API with tool calls in non-thinking mode. Online mode is enabled for `class-demo` only: construct an allowlisted payload of minimal synthetic facts/IDs, not raw witness sheets, workbook values, personal data, secrets or arbitrary text. Keep workbook investigations offline and explicitly labeled. No scraping, sending or provider-side actions other than model inference.
- Cap calls per investigation plus output tokens, use a wall-clock timeout and a configurable daily paid request/token budget enforced server-side across users and restarts. Do not call the model on UI rerender. Handle absent key, invalid output, 401/402/429, timeouts and service errors visibly without secrets, false recovery, or implicit fallback. Store only usage, status, approved trace metadata and validated drafts, not raw provider logs.
- Ship a placeholder-only `.env.example`, VPS service/proxy config templates and short deploy/runbook; do not request deployment credentials, buy or publish anything during build. Live verification is opt-in on the operator's VPS using only synthetic input; label `NOT RUN` until observed. See H1/H2.

## 7. Local-first setup and portability (current delivery priority)
- Implement and test the same Python app on Windows, macOS and Linux. Native Windows first; do not require WSL, Docker, Bash, a hard-coded installation path or a hosted service. Provide a Python setup/launcher and short OS-specific instructions, including a simple Windows launch shortcut/script. Local use binds to loopback. Remote browser access is a separate authenticated HTTPS deployment, not a reason to expose the laptop DB.
- Reuse an already installed PostgreSQL server. Detect it without changing global authentication or firewall settings. Create an isolated project database and minimally privileged app login using a local, operator-run interactive setup. Any admin password must be entered in the operator's own masked local prompt, never through agent chat, CLI arguments or logs. Do not persist admin credentials. Protect app credentials outside the repository. Stop on a naming collision with unrelated existing objects; never reset unrelated databases. No silent fallback to SQLite. If existing SQLite data is found, preserve it and request permission before a separate migration.
- Keep the workbook read-only. Add a distinctly labeled manual, hypothetical overlay by account/product/day for Bahman 16–30 and Esfand 1–29 of this scenario. Test empty, repeated and corrected entries; prevent double count and preserve revision history. Keep class-demo separate. PostgreSQL credentials never go to DeepSeek.
- Prove register/re-read, correction, repeat import, transaction rollback and persistence after app restart against PostgreSQL in an isolated test DB. Set up automated checks for all three desktop OSes. Distinguish actual platform runs from planned checks or CI configuration. Record genuine missing fixture or environment blockers; never claim passing unrun tests.
